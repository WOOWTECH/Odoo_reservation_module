## 概述

**預約管理系統** 是為 Odoo 18 社群版打造的完整預約管理系統。它將 Odoo 企業版的 Appointment 模組功能帶入社群版 — 線上預約入口、資源管理、付款處理、Discuss 頻道會議室及多語言支援。

### 為什麼選擇此模組？

| 問題痛點 | 解決方案 |
|----------|----------|
| Odoo CE 缺少預約系統 | 完整預約功能，支援 6 種預約類型 |
| 線上預約需要客製開發 | 即用型公開預約入口，路徑為 `/appointment` |
| 會議室需要第三方工具 | 內建 Discuss 頻道整合，支援視訊通話 |
| 資源排程需手動管理 | 自動化的員工、場地、設備可用性管理 |
| 收款流程獨立於預約 | 整合 Odoo 付款供應商，支援按人數收費 |
| 客戶入口無預約管理 | 入口儀表板含預約記錄、詳情及取消功能 |

## 功能特色

### 預約管理

- **6 種預約類型** — 會議、視訊通話、餐桌預訂、資源預訂、付費諮詢、付費座位
- **資源與員工排程** — 管理房間、桌位、設備及員工的每週可用時間
- **自動確認** — 依據容量規則及可用性自動確認預約
- **取消政策** — 可設定取消期限與寬限期
- **FAQ / 問答支援** — 為每種預約類型新增常見問題與解答

### 線上預約入口

- **公開預約頁面** — 精美的 `/appointment` 列表頁面，包含預約類型卡片
- **分步驟預約** — 選擇日期 → 選擇員工 → 選擇時段 → 填寫資料 → 確認
- **響應式設計** — 適配行動裝置的現代化預約流程
- **賓客資訊** — 收集姓名、電子郵件、電話、人數及備註
- **容量驗證** — 跨所有預約強制執行每時段最大容量

### 付款整合

- **Odoo 付款供應商** — 支援所有 Odoo 付款供應商（Stripe、PayPal 等）
- **按人數收費** — 每人價格自動計算總金額
- **付款後確認** — 草稿狀態預約，付款完成後自動確認
- **免費與付費** — 同一系統支援免費和付費預約類型

### Discuss 頻道會議室

- **自動建立頻道** — 確認線上會議預約 → 自動建立 Discuss 頻道
- **視訊通話支援** — 產生會議 URL 並透過郵件分享給客戶
- **入口存取** — 客戶從入口預約頁面直接進入會議室
- **成員管理** — 員工和客戶以正確權限自動加入頻道

### 權限與隱私（18.0.3.2.2 起）

- **會議室是成員制** — 線上預約的 Discuss 會議室建成 `group` 對話，只有指派員工與該預約的客戶是成員；其他 portal 客戶讀不到、也不能自行加入。需安裝 `woow_odoo_portal_discuss`（或舊名 `cs_portal_discuss`）才會建立；客戶仍可在「我的討論」看到自己的會議室。升級時 migration 會把既有會議室改成成員制，並移除不屬於該預約的成員。
- **行事曆只給相關的人看** — 預約建立的 calendar.event 與它的出席者列（訪客姓名、email、電話）只有主辦員工（指派的員工）、該預約的訪客聯絡人（`appointment_guest_partner_id`，訪客同時是已登入的 portal 客戶時才有意義）與預約管理員看得到。被列為出席者並不會取得權限：被邀請的同事打不開這筆 event；其他員工（包括沒被指派到這筆預約的預約使用者）在共用行事曆上不再看到這些 event（連「Busy」也不顯示），用名稱、出席者或時間搜尋也找不到，在訪客聯絡人的「會議」裡也看不到。不是預約建立的 event 維持 Odoo 原本的行為。event 另外設為 private，標題是「預約類型 - 預約編號」（不含訪客姓名），說明只留預約編號、人數與場地，訪客 email、電話與備註只在預約本身。改派員工時 event 主辦人跟著換成新員工。沒有指派員工時，event 不再以公開使用者當主辦人。既有 event 由 migration 一併處理。
- **預約只能從預約表單建立** — portal／公開使用者不能經 RPC 直接建立預約；前台流程不受影響。
- **員工欄位不給客戶** — 內部備註、付款失敗次數、提醒狀態與 access token 只有預約群組的員工讀得到。
- **預約表單只顯示名單內的員工／場地** — 網址帶的 staff_id／resource_id 必須屬於該預約類型的有效名單才會顯示。
- **預約 event 的視訊會議室** — 沒裝 portal Discuss、預約類型也沒設視訊連結時，第一次「加入視訊會議」由 Odoo 建立的會議室只放主辦員工（指派的員工）與該預約的訪客，不看 event 上還列了誰。從聯絡人的「會議」掛上或拿掉預約 event 時，event id 不論用哪種寫法送（`63`、`"63"`、`63.0`）都會檢查；不是 id 的值直接拒絕。
- **預約只用自己的訂單** — 預約只能連到自己的訂單：訂單裡有這筆預約加進去的行、同一個客戶的訂單，或匿名訪客的共用購物車。（這個版本以前，每筆匿名預約都會建一個新的訪客聯絡人，訪客的共用購物車又被改指向最新那筆預約的聯絡人，所以同一購物車裡較早的預約帶的是別的訪客聯絡人。「訪客聯絡人」是沒有人能用它登入的有效聯絡人：它與它所屬公司都沒有使用者，已封存的使用者也算。訪客的預約屬於聯絡人是訪客的購物車，或購物車裡有網站替這筆預約加的區段行的購物車；訪客付款前先登入時購物車會改指向帳號的聯絡人，區段行仍留在裡面。portal 可直接建立預約的漏洞需要登入，所以那些列永遠不是訪客。）升級不解除訂單、不清付款交易；付款狀態只重算「訂單是自己的」且還沒確認的預約，已確認、已完成的預約與訂單不是自己的預約都維持原狀（真的已付款的維持已付款；唯一會被改回待付款的，是舊規則下因同一購物車其他品項的已付發票而被標成已付款的未確認預約，預約上會留記事）。舊資料裡指向別的客戶訂單的預約（之前 portal 可直接建立預約，或早期手動連結）會在預約上留內部記事，還要處理的預約另給預約管理員一個待辦；連結與狀態維持原樣；升級前可先執行 `migrations/18.0.3.2.2/post-migrate.py` 裡唯讀的 `PRE_UPGRADE_CHECK_SQL`，列出這些預約。這類訂單的付款不會保留、標成失敗或確認該預約，取消該預約也不會動到那張訂單；「預約已收到」與「付款失敗」信的付款連結與金額只取預約自己的訂單，資料庫裡已存的翻譯版本也一併改正。這類預約可能還留著舊規則從那張訂單的發票給的「已付款」，升級不去改它；但任何讓預約往下走的動作都不讀儲存的付款狀態：確認需付款的預約（員工操作，或付款後自動確認）時，當下只依預約自己的訂單與付款交易判斷，所以這類預約在自己的訂單付清之前確認不了（訊息會指出不被採計的訂單）；儲存的付款狀態也會隨預約或訂單的聯絡人改變而更新。

### 預約規則（18.0.3.2.2 起）

- **整團人數要放得下** — 已佔人數加上這次的人數不能超過場地容量；表單、確認與自動分配場地都照這條（容量 0 視為 1）。沒選場地時，表單上限是名單裡最大的場地。
- **不再建立未指派的預約** — 自動分配員工或場地時，名單裡在那個時段都沒空（或沒排班）就直接拒絕，不會建出沒人、沒場地的預約。
- **活動模式一次預約整個時段** — 活動型預約必須剛好是一個可預約時段（結束在 24:00 的時段，結束時間是隔天當地 00:00）；縮短、拉長或切段的區間都會被拒絕。
- **員工／場地專屬的排班** — 限定某位員工或某個場地的可預約時段，只套用在該員工或場地，表單與自動分配都一樣。
- **日光節約時間切換日** — 可預約時段的時間是預約類型時區的牆上時間，一個時段長 `slot_duration` 的實際時間，預約存的也是這個長度。時鐘切換的那一天，橫跨切換的時段，結束時間就是預約會存下的結束時間（不會差一小時）；開始或結束落在不存在的牆上時間的時段窗口，不會被列出也不能預約（時段清單與預約表單用同一組窗口；在少數午夜切換時鐘的時區，前一天結束在 24:00 的晚間窗口也算在內）；出現兩次的牆上時間一律當成標準時間。沒有日光節約時間的時區（例如 Asia/Taipei）不受影響。
- **公開頁面會檢查預約類型** — 封存或未發佈的預約類型不會列出，也不能排時段或預約；/slots 與 /schedule 只接受該類型有效名單內的員工與場地。
- **付款保留名額** — 需付款的預約在付款期間保留時段（`reservation_module.payment_hold_minutes`，預設 30 分鐘；0 表示不保留）；已開始但尚未完成的付款（例如轉帳）保留較久（`reservation_module.payment_pending_hold_hours`，預設 48 小時）；付款完成後保留到員工確認。建立付款交易前會重新檢查時段，已被別人訂走就不收款。已付款卻無法自動確認的預約會標成「已付款未確認」，並留言、建立待辦給員工處理。
- **取消已付款的預約不會取消那筆款項** — 已完成或已授權的付款交易，以及全部或部分已付的發票，會讓訂單保持原狀並建立給管理員的退款待辦。已過帳的折讓單只是會計文件，不代表客戶已收到退款；退款或關閉待辦前須核對金流與銀行紀錄。只有付款交易中已完成的退款子交易會減少該交易持有的款項。已取消的預約即使只收到訂金，也可能顯示「已付款」；確認預約仍須全額付清。共用購物車的金流退款後，須補足整張訂單才可確認其中任何預約；若仍有未退的淨收款，付款頁會拒絕再次收取全額，須由員工對帳補足差額。每筆預約在各語言下最多只有一個未完成的退款待辦。舊版共用購物車的訂單行未綁定預約，無法可靠區分各預約的款項，退款前須核對整張訂單。
- **被拒絕的付款不留下東西** — 建立付款交易時被拒絕（付款頁與付款之間，預約已被付清或時段已被訂走），交易與檢查已寫下的資料會一起回復，即使呼叫端接住這個拒絕後繼續執行（預約付款頁的路由就是這樣）：預約上不會留下草稿交易。
- **預約付款頁付完後，該預約的行離開購物車** — 預約自己的付款頁（`/appointment/payment/...`）只收這筆預約的行。付款完成後，這些行會從訪客的購物車移到各自的訂單並確認該訂單（購物車裡只有這筆預約時，直接確認那張購物車，和結帳一樣），因此同樣的行不會再被結帳頁或報價單連結重複收款；購物車的其他品項不受影響，仍可付款。預約維持綁定該付款交易。已付款、已取消或已結束的預約，付款頁不再收款；訂單裡有已付款預約的行時，訂單也不再收款。模組不替這張訂單開發票：由員工開立並對帳，與一般付款頁付款相同。未涵蓋：兩筆款項同時發起（一筆在付款頁、一筆在結帳頁）只有金流端能擋；18.0.3.2.2 以前建立的預約（它們的行分不出來）不會被搬移。
- **付款商品未上架** — 網站拒絕某個付款商品（未上架、已封存）時，預約表單與預約的付款連結會顯示「付款設定錯誤」頁，而不是單純的 400，購物車裡也不會留下半成品。含預約的購物車不能被清空或併入別的購物車；訊息會指出是哪筆預約，並說明要先取消預約。
- **防濫用限制** — 除了每個信箱／電話每小時 5 筆（`Foo@x.com` 與 `foo+1@x.com` 算同一個信箱），另外限制同一個來源位址（`reservation_module.booking_rate_limit_per_ip`，預設每小時 20 筆；指的是訪客在代理伺服器後面的實際位址，見「安全與部署注意事項」）、同一個登入客戶（每小時 5 筆）與同一個預約類型（`reservation_module.booking_rate_limit_per_type`，預設每小時 100 筆）；設 0 表示不限。公開預約寄給同一個信箱的通知信有上限（`reservation_module.guest_mail_daily_limit`，預設 24 小時內 10 筆預約）；超過後仍可預約，但不再寄信。

### 客戶入口

- **我的預約儀表板** — 入口用戶可查看所有預約的狀態、類型及日期
- **預約詳情頁面** — 完整預約資訊，含「開啟會議室」及「取消預約」操作
- **我的討論** — 從入口存取所有會議室頻道的中央樞紐
- **狀態追蹤** — 即時預約狀態（草稿、已確認、已取消）

### 電子郵件通知

- **確認信件** — 自動發送包含預約詳情、會議連結及日曆附件的郵件
- **提醒系統** — 可設定預約前的郵件提醒
- **會議 URL** — 線上會議預約的所有郵件均包含 Discuss 頻道 URL
- **時區** — 郵件日期使用預約類型的時區；升級時 migration 會修補資料庫裡已儲存的舊繁中郵件日期元件，避免由排程寄出時顯示 UTC。

### 多語言支援

- **英文** — 完整介面及郵件模板
- **繁體中文 (zh_TW)** — 針對台灣市場的完整翻譯
- **簡體中文 (zh_CN)** — 部分介面已有翻譯；尚未翻譯的預約郵件使用英文
- **可擴展** — 標準 Odoo `.po` 翻譯格式，易於新增語言

## 安裝說明

### 前置需求

- **Odoo 18.0** 社群版
- **PostgreSQL 13+**
- **Python 3.10+**

### 步驟一：部署模組

```bash
# 複製倉庫
git clone https://github.com/WOOWTECH/Odoo_reservation_module.git

# 複製到 Odoo 附加模組路徑
cp -r Odoo_reservation_module/reservation_module /path/to/odoo/addons/

# 更新模組列表並安裝
./odoo-bin -u reservation_module -d your_database
```

### 步驟二：在 Odoo 中安裝

1. 前往 **應用程式** 選單
2. 點擊 **更新應用程式列表**
3. 搜尋 **「Reservation Booking Enhancement」**
4. 點擊 **安裝**

### 步驟三：設定付款（選用）

如需付費預約：

1. 前往 **記帳 > 設定 > 付款供應商**
2. 啟用並設定您偏好的供應商（Stripe、PayPal 等）
3. 模組會自動使用已設定的付款供應商處理付費預約類型

## 設定指南

### 1. 建立預約類型

前往 **行事曆 > 預約**

1. 點擊 **建立** 新增預約類型
2. 設定 **名稱**、**描述** 及 **預約分類**（會議、視訊通話、餐桌、資源、付費諮詢、付費座位）
3. 選擇 **地點類型**：實體、線上會議或客戶地點
4. 指派可處理此預約類型的 **員工**
5. 視需要啟用 **允許客戶選擇員工**

### 2. 設定可用時間

在預約類型表單中，前往 **可用時間** 頁籤：

1. 新增每週可用規則（星期幾 + 時間範圍）
2. 設定 **時段長度**（例如 30 分鐘、1 小時）
3. 設定 **最早/最晚預約** 窗口
4. 設定每時段的 **最大容量**（用於餐桌/資源預訂）

### 3. 設定付款選項

在 **選項** 頁籤：

1. 啟用 **需要付款**
2. 設定 **每人價格**（或固定價格）
3. 連結 **產品** 以產生銷售訂單
4. 設定取消期限

### 4. 設定 Discuss 整合

用於線上會議類型：

1. 將 **地點類型** 設為「線上會議」
2. （選用）設定 **視訊會議連結** 作為會議 URL
3. 系統在預約確認時自動建立 Discuss 頻道
4. 入口用戶自動加入其預約的頻道

### 5. 新增 FAQ / 問答

在 **問題** 頁籤：

1. 新增常見問題及解答
2. 這些會顯示在公開預約頁面

### 6. 發佈

切換 **已發佈** 開關，使預約類型在 `/appointment` 上可見。

### 安全特性

- **記錄規則** — 使用者僅能依據其群組檢視/修改預約
- **入口隔離** — 入口用戶僅能看到自己的預約和頻道
- **CSRF 防護** — 所有表單提交均包含 CSRF 令牌
- **付款驗證** — 伺服器端付款驗證，確認付費預約前先驗證付款
- **Discuss 頻道限制** — 僅線上會議預約建立頻道；成員僅限預約相關方

### 安全與部署注意事項

把 18.0.3.2.2（或更新版本）部署到既有資料庫之前請先讀這一節。

**程式與升級要一起做。** 部署新程式的同一次變更內要執行 `-u reservation_module`。這個版本新增了儲存欄位（`sale.order.line.appointment_booking_id`／`appointment_booking_qty`、`calendar.event.is_appointment_booking`／`appointment_guest_partner_id`、`payment.transaction.appointment_failure_notified`，以及 `appointment.booking` 上的付款保留、付款失敗與 `client_ip_hash` 欄位），而 `migrations/18.0.3.2.2/` 只有在 `-u` 時才會執行；沒升級的資料庫，網站與後台會因為缺欄位而出錯。升級可以重複執行，不會解除任何銷售訂單的連結、也不會清掉付款交易，並會改寫既有的預約行事曆 event 與預約 Discuss 會議室（見下）。Helm 站台：直接改 Pod 會被下一次 `helm upgrade` 蓋回，請把新版模組放進映像或 chart，Pod 跑起來之後再執行一次 `-u`。

**仍需營運控管的限制。** 行事曆追蹤者資料、舊的 Odoo 視訊會議室成員，以及聯絡人合併，仍可能在本模組的預約權限之外透露資訊或轉移存取權；請檢查既有紀錄並限制聯絡人合併。未完成的付款預設最多可佔用時段 48 小時，請依情況調整參數並監看濫用。持有預約付款連結的人可能透過 Odoo 的 token 付款流程選用已儲存的付款憑證；請妥善保護連結，並檢查金流服務的 token 政策。若安裝 `wassa_reservation`，其容量橋接尚未計入付款保留及本次整團人數；開放需付款且有容量限制的預約前，須先修補該套件。這些是部署限制，本版不保證解決。

**系統參數**（設定 → 技術 → 系統參數；整數；沒有這個參數或格式不對時用預設值）：

| 參數 | 預設 | 說明 |
|------|------|------|
| `reservation_module.booking_rate_limit_per_ip` | 20 | 公開表單每個來源位址每小時的預約筆數（見下面的「代理伺服器後面的來源位址」）。0 表示不限 |
| `reservation_module.booking_rate_limit_per_type` | 100 | 公開表單每個預約類型每小時的預約筆數，整個網站共用。0 表示不限 |
| `reservation_module.guest_mail_daily_limit` | 10 | 公開表單預約寄給同一個信箱的通知，24 小時內有幾筆預約還會寄信（模組的信件，以及行事曆邀請、改期與提醒信）；超過後仍可預約，但不再寄信。0 以下表示不限 |
| `reservation_module.payment_hold_minutes` | 30 | 需付款的預約保留時段的分鐘數。0 以下表示不保留 |
| `reservation_module.payment_pending_hold_hours` | 48 | 已開始但尚未完成的付款（例如轉帳）可延長一次的保留小時數，每筆預約只給一次，也不會超過預約結束時間。0 以下表示不延長 |
| `reservation_module.payment_failure_mail_limit` | 3 | 每筆預約「付款失敗」信的總數上限（另外每 24 小時最多一封）。0 以下表示不限總數 |
| `reservation_module.payment_failure_note_limit` | 5 | 每筆預約在討論串留下的付款失敗記事數上限。0 以下表示不留記事（失敗次數仍會累計） |

不是參數的限制：同一個信箱或電話每小時 5 筆（`Foo@x.com` 與 `foo+1@x.com` 算同一個信箱）、同一個登入客戶每小時 5 筆。所有限制都是軟性的：同一瞬間送來的請求可能多過幾筆。

**代理伺服器後面的來源位址。** `booking_rate_limit_per_ip` 要算的是一位訪客，不是 Odoo 前面的 tunnel 或代理：在 PaaS chart（cloudflared tunnel、nginx sidecar、`proxy_mode = True`）後面，或單純的 tunnel 後面，Odoo 的 `remote_addr` 對每位訪客都是同一個私有位址，這樣限制就會變成整個網站共用一個。所以模組自己判斷位址（`client_address.py`），不管 `proxy_mode` 怎麼設：

1. 連到 Odoo 的連線來自公開位址時，那就是訪客，轉送標頭一律不採信（任何人直接連得到伺服器時都能自己送這些標頭）。
2. 連線來自私有、loopback、link-local 或 CGNAT 位址（tunnel、ingress、sidecar）時，訪客依序取：`CF-Connecting-IP`（Cloudflare 設的）若是公開位址；否則 `X-Forwarded-For` 由右往左第一個公開位址（每一站都把自己看到的位址加在右邊，所以訪客寫在左邊的內容贏不了）；再不然 Odoo 的 `remote_addr` 若是公開位址。
3. 找不到公開位址時，這個請求不套用「每個來源位址」的限制（絕不把這類訪客全部併成一個共用 key）；預約仍記為公開表單的預約，來源是 `unknown`，所以信箱、預約類型與寄信的限制照樣有效，日誌也會留一行 INFO。
4. IPv6 訪客依 /64 計算，IPv4-mapped IPv6 位址視為對應的 IPv4 位址，不是單純位址的值（含埠號、括號、名稱、`unknown`、亂碼）一律忽略。資料庫只存加了密鑰的雜湊（`client_ip_hash`，只有預約群組的員工讀得到），不存位址本身。

PaaS chart 或 Cloudflare tunnel 後面不需要設定任何東西。第一站是公開位址時，這一站會被當成訪客：Cloudflare 紀錄直接指向公開的來源位址，或 Odoo 前面是公開的負載平衡器，每位訪客看起來都是同一個位址，這種站請把 `booking_rate_limit_per_ip` 設成 0。代理不是 Cloudflare 時，請讓它丟掉或改寫訪客自己送的 `CF-Connecting-IP`，否則訪客可以自己挑 key；其他限制仍然有效。

**要告知團隊的行為變更**

- **預約的行事曆 event** 只有指派員工（主辦人）、該預約的訪客聯絡人與預約管理員看得到；被邀請的同事打不開，其他員工連「Busy」區塊都看不到，所以共用行事曆會少掉這些區塊。這兩條記錄規則是 `noupdate="0"`：在資料庫裡改過的內容，每次升級都會被蓋回。標題是「預約類型 - 預約編號」，說明不含 email、電話與備註。
- **線上預約的 Discuss 會議室** 是成員制的 `group` 對話：成員是指派員工（沒有指派員工時是確認預約的內部使用者）與該預約的訪客；其他 portal 使用者不能再讀、也不能加入。升級會把既有會議室轉換過來並移除外人。只裝了 `woow_odoo_portal_discuss`（沒有 `cs_portal_discuss`）的站，線上預約從這個版本起也會開會議室。
- **預約只用自己的銷售訂單**：訂單裡有這筆預約加進去的行、同一個客戶（同一個 commercial partner）的訂單，或（這個版本以前建立的訪客預約）訪客的共用購物車。其他連結一律以驗證錯誤拒絕，員工與 `sudo` 也一樣。員工要把預約連到別的客戶的訂單（代付）時，先把預約的客戶（partner）改成那位客戶，再連訂單。舊資料裡已經指向別的客戶訂單的預約會保留並在預約上留記事，不會被解除；升級前可先執行 `migrations/18.0.3.2.2/post-migrate.py` 裡的 `PRE_UPGRADE_CHECK_SQL` 列出這些預約。
- **預約只能從預約表單建立**；portal 與公開使用者對 `appointment.booking` 只有讀取權限，不能經 RPC 建立預約。內部備註、access token、提醒狀態、付款失敗次數與付款保留欄位只有預約群組的員工讀得到。
- **寄到訪客填的信箱的信**（表單接受任何位址）：信裡只有預約編號與訪客填的姓名（最多 256 字元，已跳脫），訪客寫的其他內容都不會出現，備註與電話不會進信。姓名是信件濫用問題接受的殘留風險：要完全拿掉，得先驗證信箱，那會改變匿名預約的流程。上面的限制只能壓住數量。

**markstudio／mujimed：切到 3.2.0 以上後，每個預約類型都要手動設定預約表單。** 18.0.3.2.0 起，必填的訪客欄位與人數改成每個預約類型的設定（預約類型的「選項」頁籤 → 「預約表單」：「姓名必填」、「Email 必填」、「電話必填」、「每筆預約限 1 人」）。預設值等於先前 main 分支的表單：姓名與 email 必填、電話選填、每筆可多人。這兩個站要自己把每個預約類型改成姓名與 email 不必填、電話必填、每筆 1 人；升級不會替你設定，沒設之前表單問的仍是 main 分支的欄位。email 與電話至少要有一項必填。
